The happy path is the easy part. Figr maps the states that actually break products:

- **Input and data**: empty, loading, partial data, validation errors
- **Access and session**: permission states, access changes, session expiry
- **System and network**: error states, retries, network failures, slow connections
- **Money and destructive actions**: payment failures, confirmation steps, deletes

## Map a flow

<Steps>
  <Step title="Describe the journey">
    Say who the user is, where they start and what they're trying to do. Attach your [Context Pod](/product-intelligence/context-pods) so the flow follows how your product works today.
  </Step>
  <Step title="Review the flow on the canvas">
    Figr draws the flow as an editable diagram with steps, decisions and branches. Check the happy path first, then the branches.
  </Step>
  <Step title="Refine it">
    Ask for a missing step or another branch, like "Add what happens when the invite email bounces." You can also edit the diagram directly.
  </Step>
</Steps>

## Example prompts

- "Map the file upload flow, including file too large, unsupported type, network failure, storage limit and access revoked."
- "Map the billing upgrade flow, including payment failure, expired card, permission restriction and downgrade impact."
- "Map the password reset flow, including invalid email, expired link, used link, rate limit and success."

## Turn states into screens

Once a prototype exists, open its **Screens** view to see every route and state on one board, with loading, empty, error and success states as separate frames. Click **Generate screens** and Figr proposes and builds the states that are missing.

Export the whole board to Figma in one run with **Export all screens**.

## Why it matters

Edge cases aren't a nice-to-have. They're the product. When the flow is mapped before any screen is polished, designers see which states to build, engineers see the behavior to expect, and PMs get a sharper spec.
